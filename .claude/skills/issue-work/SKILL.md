# issue を着手から完了まで進める

$ARGUMENTS

規約は `.claude/rules/issues.md`、委譲の作法は `.claude/rules/orchestration.md` にあります。

## 1. 対象を決める

指定がなければ `/issue-triage` で次の 1 件を決めてから戻ってきてください。

対象の issue ファイルを読み、次を確認します。

- **達成条件** — これがこの作業の完了定義になります。曖昧なら着手前に直す
- **不変条件への影響** — 「あり」なら、**着手前にユーザーに確認**する。専門エージェントに委ねない
- **影響範囲** — 触るクレート、設定、ドキュメント。ここが実装のブリーフィングの土台になる

## 2. progress へ移す

```bash
git mv management/issues/todo/<file> management/issues/progress/
```

frontmatter に `started: <date +%F>` を追記します。ファイル名は変えません。

## 3. 設計を確認する（必要な場合）

新しい概念・新しいポート・層をまたぐ変更を含むなら、実装前に `domain-specialist-agent` に
配置の妥当性を判断させます。実装してから「層が違う」と言われるのが最も高くつきます。

## 4. 実装する

`impl-agent` に委譲します。ブリーフィングに含めるもの:

- **issue ファイルのパス**（達成条件と影響範囲をそこから読ませる）
- 触ってよい／触ってはいけないファイル
- これまでにわかっていること、既に試して駄目だったこと
- 完了条件 = issue の達成条件 + `make check` が緑

着手中に分かったことは issue の「メモ」に追記します。次に読む人（自分を含む）のためです。

## 5. レビューする

`/review-panel` を使うか、変更の性質に応じて必要なレビューだけを並列で起動します。
指摘は検証してから採用します（誤検知はあります）。

## 6. 達成条件を突き合わせる

**チェックボックスを 1 つずつ確認します。** 満たしていない項目があれば done に移しません。

- 全部満たした → 7 へ
- 一部だけ満たした → progress のまま。残りをメモに書き、ユーザーに状況を報告する
- 途中で範囲が変わった → 達成条件を書き換えるのではなく、**別 issue に切り出す**ことを検討する

## 7. done へ移す

```bash
git mv management/issues/progress/<file> management/issues/done/
```

frontmatter に `completed: <date +%F>` を追記し、末尾に結果を書きます。

```markdown
## 結果

- <何をしたか。変更したクレート／ファイルの要点>
- <達成条件をどう満たしたか（テスト名など、後から辿れる形で）>
- <やらなかったこと、別 issue に切り出したもの>
```

## 8. 報告する

`make check` が緑であることを確認してから、完了と結果、残した issue を伝えます。
