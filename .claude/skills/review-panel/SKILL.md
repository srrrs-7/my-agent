# 3 種のレビューを並列で走らせて統合する

$ARGUMENTS

## 1. 差分を把握する

```bash
git status --porcelain
git diff HEAD --stat
```

untracked のファイルは `git diff` に出ません。**変更の全体像を把握してからレビューに投げてください**
（過去に、untracked を理由に「ファイルが存在しない」という誤検知を受けたことがあります）。

## 2. 3 つを並列で起動する

1 メッセージ内に複数の Agent 呼び出しを書くと同時に走ります。各ブリーフィングに含めるもの:

- 変更の目的（1〜2 文）
- 変更されたファイルの一覧（untracked を含む）
- レビューの観点（そのエージェントの定義にあるので繰り返さなくてよい）
- 「指摘がなければ『なし』と明言すること」

| エージェント | 呼ぶ条件 |
|---|---|
| `security-review-agent` | パス解決・ファイル操作・設定・依存・Docker に触れた |
| `performance-review-agent` | ループ・履歴・走査・HTTP クライアントに触れた |
| `domain-specialist-agent` | 新しい概念・ポート・層をまたぐ変更をした |

該当しないものは呼ばない。

## 3. 指摘を検証する

**鵜呑みにしない。** 各指摘について次を確認します。

1. 指摘された場所を実際に読む
2. 「その指摘が正しいとしたら、どのテストが落ちるはずか」を考える。
   落ちるはずのテストが通っているなら、指摘か自分の理解のどちらかが間違っている
3. 具体的な失敗シナリオ／条件が書かれていない指摘は、書けるかどうかを自分で試す。書けないなら見送る

## 4. 統合して提示する

重要度順に並べ、それぞれについて **採用 / 見送り** と理由を書きます。

```
### 採用
1. [security/high] <要約> — <なぜ直すか>
### 見送り
1. [performance/小] <要約> — <なぜ見送るか>
### 誤検知
1. <要約> — <なぜ誤りか>
```

採用分は `impl-agent`（修正）または `refactor-agent`（構造改善）に渡します。
レビューエージェントは編集ツールを持たないので、自分では直しません。

## 5. 仕上げ

```bash
make check
```

緑になってから完了と報告します。
