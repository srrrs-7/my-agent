# 開発タスクを専門エージェントで進める

$ARGUMENTS

まず `.claude/rules/orchestration.md` を読んでください（委譲の判断基準、ブリーフィングの型、
返却の契約、並列実行の規則）。以下はその適用手順です。

## 1. 範囲を決める

- 要求を読み、**何が完了条件か**を一文で書く
- 曖昧さが成果物を変えるなら、着手前にユーザーに確認する
- 不変条件（`.claude/rules/invariants.md`）に触れそうなら、ここで気づいて明示する

小さい変更（1〜2 ファイル、既存パターンの踏襲）なら、以降の段階を飛ばして自分で実装してよい。
**飛ばすことを明示的に決める**のが要点で、なんとなく省くのとは違う。

## 2. 設計を確認する（必要な場合）

新しい概念・新しいポート・層をまたぐ変更なら、実装前に `domain-specialist-agent` に配置を判断させる。

実装してから「層が違う」と言われるのが最も高くつくので、迷ったら先に聞く。

## 3. 実装する

`impl-agent` に委譲する。ブリーフィングには必ず含める:

- 目的（1〜2 文）
- 触ってよい／触ってはいけないファイル
- **これまでにわかっていること、既に試して駄目だったこと**
- 完了条件（通常は `make check` が緑 + 新しいテスト）

## 4. テストを固める

`impl-agent` が足したテストで足りるかを判断する。不変条件に関わる変更、
または退行しやすい細部（境界値・順序・エラー経路）を含む場合は `test-agent` に追加させる。

## 5. レビューする（並列）

1 メッセージ内で複数の Agent 呼び出しを出して同時に走らせる。

| 変更の性質 | 呼ぶエージェント |
|---|---|
| パス解決・ファイル操作・設定・依存・Docker | `security-review-agent` |
| ループ・履歴・走査・HTTP クライアント | `performance-review-agent` |
| 新しい概念・ポート・層をまたぐ変更 | `domain-specialist-agent` |

全部を毎回呼ばない。関係ないレビューはノイズを生む。

## 6. 統合する

- 指摘を**検証してから**採用する。「その指摘が正しいならどのテストが落ちるか」を考えると誤検知が落ちる
- 採用分を `impl-agent`（修正）または `refactor-agent`（構造改善）に渡す
- 見送る指摘は、見送った理由を記録してユーザーに伝える

## 7. 報告する

- `make check` が緑であることを確認してから完了と言う
- 専門エージェントの報告を転送しない。要点を統合して伝える
- やらなかったこと・残した問題を明示する
