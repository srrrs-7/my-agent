# マルチエージェント運用

## 前提: 誰が root か

**root セッション（このセッション）が orchestrator です。**
`claude --agent orchestrator` で起動した場合も同じ役割になります。

専門エージェントは**葉**です。互いを呼び出しません（定義で `Agent` ツールを外してあります）。
分解・統合・最終判断はすべて root が行います。理由は 2 つ:

- 専門エージェントは独立したコンテキストで動くため、他のエージェントが何を見たか知りません
- 委譲の階層が深くなるほど、判断の根拠が root から見えなくなります

## 委譲の判断

**委譲する**のは次の場合です。

- 調査の過程（大量のファイル読み、ログ、検索結果）が root の文脈を圧迫する
- 同じ種類の作業を繰り返す
- 独立した視点が必要（レビュー、対抗仮説）
- 並列化できる独立した作業がある

**委譲しない**のは次の場合です。

- 1〜2 ファイルの自明な編集
- ユーザーとの対話・確認が必要な判断
- 不変条件を変えるかどうかの決定（root が判断し、必要ならユーザーに確認する）

| やりたいこと | エージェント |
|---|---|
| 機能追加・バグ修正 | `impl-agent` |
| 振る舞いを変えない構造改善 | `refactor-agent` |
| テストの追加・失敗の調査 | `test-agent` |
| 層の境界・ドメインモデルの妥当性判断 | `domain-specialist-agent` |
| サンドボックス・秘密情報・依存の安全性 | `security-review-agent` |
| 計算量・確保・並行性 | `performance-review-agent` |
| issue の起票・整形・棚卸し | `issue-agent` |

## ブリーフィングの型

専門エージェントは**このリポジトリの文脈を持っていません**。CLAUDE.md は読めますが、
今何が起きているかは知りません。委譲時は必ず次を含めてください。

```
## 目的
（1〜2 文。何のための変更か）

## 範囲
触ってよいファイル / 触ってはいけないファイル

## 文脈
これまでにわかっていること。既に試して駄目だったこと。関連する直近の変更

## 完了条件
何が真になれば終わりか（例: `make check` が緑 + 新しいテストが失敗を再現する）

## 返してほしいもの
（下の「返却の契約」を指定する）
```

「これまでにわかっていること」を省くと、同じ調査を最初からやり直します。ここが最も効きます。

## 返却の契約

| エージェント | 返すもの |
|---|---|
| `impl-agent` / `refactor-agent` / `test-agent` | 変更したファイルと理由、`make check` の結果、残した既知の問題 |
| レビュー系 3 種 | 重要度順の指摘。各指摘に「ファイル:行」「なぜ問題か」「具体的な失敗シナリオ」。指摘なしなら「なし」と明言 |

レビュー系は**修正しません**。指摘だけを返し、適用するかは root が決め、`impl-agent` に渡します。
定義で `Write` / `Edit` を外してあるので、通常の経路では編集できません
（`Bash` は `git diff` と `make check` のために残してあります）。

## 並列実行

独立した作業は 1 メッセージ内で複数の Agent 呼び出しにまとめると同時に走ります。

- **レビューは並列でよい** — 3 種のレビューは互いに独立です
- **編集は並列にしない** — 同じファイルを触ると衝突します。どうしても必要なら `isolation: worktree` を検討
- **調査は並列でよい** — 別々のサブシステムを別々に読む場合

## 典型的な流れ

```
1. root: 計画を立て、必要なら plan mode でユーザーに確認
2. root: 大きい変更なら domain-specialist-agent に設計の妥当性を先に確認
3. impl-agent: 実装
4. test-agent: テスト追加（実装と同じエージェントに任せないと決めた場合）
5. 並列: security-review-agent + performance-review-agent + domain-specialist-agent
6. root: 指摘を統合し、採用するものを決める
7. impl-agent or refactor-agent: 採用分を適用
8. root: make check → ユーザーに報告
```

小さな変更で全段階を回す必要はありません。**段階の省略は root が明示的に決めること**で、
なんとなく飛ばすのとは違います。

## やってはいけないこと

- レビュー結果を検証せず鵜呑みにする。誤検知はあります（実際に「ファイルが存在しない」という
  誤検知を受けたことがあります — untracked だっただけでした）
- 専門エージェントの報告をそのままユーザーに転送する。root が要点を統合して伝える
- 「念のため」全エージェントを毎回起動する。トークンと時間の無駄です
- 不変条件（`invariants.md`）の変更を専門エージェントに委ねる。root が判断し、ユーザーに確認する
