# Issue 管理

## 置き場所とステータス

```
management/issues/
  TEMPLATE.md     起票時にコピーする雛形
  todo/           未着手
  progress/       着手中
  done/           完了
```

**ステータスはディレクトリが唯一の真実です。** frontmatter に `status:` を書かないでください。
2 箇所に持つと必ずずれます。状態遷移はファイルの移動です。

```bash
git mv management/issues/todo/<file> management/issues/progress/
git mv management/issues/progress/<file> management/issues/done/
```

`done/` が 50 件を超えたら年別（`done/2026/`）にまとめてよい。ファイル名は変えません。

## ファイル名

```
<作成日>_<英小文字ケバブのタイトル>.md
例: 2026-08-14_streaming-response-support.md
```

- 作成日は `date +%F` で取得する（推測しない）
- タイトル部分は ASCII 小文字・ハイフン区切り。frontmatter の `title` は日本語でよい
- 同じ日に複数起票してもタイトルで区別できる。ファイル名は**移動しても変えません**
  （作成日は作成日のままであり、着手日・完了日ではない）

## frontmatter

```yaml
---
title: ストリーミング応答に対応する    # 日本語可。一文で
created: 2026-08-14
urgency: medium                        # xhigh | high | medium | low
importance: high                       # xhigh | high | medium | low
priority: P1                           # 下の表から導出する（手で決めない）
scope: [infrastructure, application, cli]
---
```

`started:` は progress へ移すとき、`completed:` は done へ移すときに追記します。
これらは日付であってステータスではありません。

## 緊急度と重要度

**重要度** — 放置したときプロジェクトのゴールにどれだけ響くか。

| 値 | 意味 |
|---|---|
| `xhigh` | 不変条件が壊れている / セキュリティ / まともに使えない |
| `high` | 主要な機能が欠けている、または回避策が高コスト |
| `medium` | 改善。実用的な回避策がある |
| `low` | あると嬉しい。無くても困らない |

**緊急度** — 今やらないと後でどれだけ高くつくか。

| 値 | 意味 |
|---|---|
| `xhigh` | 今動かない、または他の作業を止めている |
| `high` | 次のまとまった作業の前提になっている |
| `medium` | 期限はないが、遅れるほど手戻りが増える |
| `low` | いつやってもコストは変わらない |

## 優先度の導出

`score = 重要度 × 2 + 緊急度`（`xhigh`=4, `high`=3, `medium`=2, `low`=1）。
重要度を 2 倍にするのは、緊急なだけの作業に押し流されないためです。

| 重要度＼緊急度 | low | medium | high | xhigh |
|---|---|---|---|---|
| **xhigh** | 9 → **P1** | 10 → **P1** | 11 → **P0** | 12 → **P0** |
| **high** | 7 → **P2** | 8 → **P1** | 9 → **P1** | 10 → **P1** |
| **medium** | 5 → **P2** | 6 → **P2** | 7 → **P2** | 8 → **P1** |
| **low** | 3 → **P3** | 4 → **P3** | 5 → **P2** | 6 → **P2** |

バックログの全順序は **P 昇順 → score 降順 → `created` 昇順（古い方が先）**。
ここまで決めてあるので、優先順位に議論の余地はありません。議論すべきなのは
`urgency` と `importance` の値そのものです。

## 必須セクション

`TEMPLATE.md` の 4 つは省略できません。

| セクション | 書くこと | よくある失敗 |
|---|---|---|
| **As-is / To-be** | **ユーザー視点**で、今どうなっていて、どう変わるか | 実装の話を書く（「`Arc` にする」は To-be ではない） |
| **影響範囲** | 触るクレート、不変条件、設定・ドキュメント、利用者への影響 | コードだけ書いて `.env.example` や README を忘れる |
| **達成条件** | チェック可能な箇条書き | 「ちゃんと動く」のように検証不能 |
| **優先度の根拠** | なぜその緊急度・重要度か（1〜2 文） | 空欄。後から誰も再評価できなくなる |

「不変条件への影響」は必ず埋めます（`.claude/rules/invariants.md` のどれに触れるか、なければ「なし」）。
ここが「あり」の issue は、着手前に root が判断します。

## いつ起票するか

**起票する**

- そのセッションで着手しない作業
- 他の作業と優先順位を比べる必要があるもの
- 見つけたが今の作業範囲外の問題（レビュー指摘の見送り分を含む）

**起票しない**

- 今すぐやる 1〜2 ファイルの作業
- セッション内の手順分解 → `TodoWrite` を使う（issue はセッションを跨ぐバックログ）

## 関連

- 起票: `/issue-new`
- 着手から完了まで: `/issue-work`
- 棚卸しと次の 1 件の決定: `/issue-triage`
- 専任: `issue-agent`（`management/issues/` の外は書き換えません）
