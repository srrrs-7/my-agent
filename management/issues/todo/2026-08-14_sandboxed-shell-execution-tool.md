# シェル実行ツール（別コンテナ・ネットワーク遮断で隔離）

## As-is（現状）

モデルはファイルの読み書き・検索しかできず、ビルドやテストを実行できない。
コード変更を頼んでも、エージェントは「動くかどうか分からない変更」を提案するに留まり、
検証（`make check` 相当）は毎回ユーザーが自分で行って結果を伝え直す必要がある。
この往復がエージェントに任せる価値を大きく削っている。

## To-be（あるべき姿）

モデルが変更後にテスト・ビルドを自分で実行して結果を確認し、失敗していれば
自分で直してから報告してくる。ユーザーは「実行して結果を貼る」係から解放される。
実行は隔離環境（ネットワーク遮断・ワークスペース外アクセス不可）の中で行われ、
ホストにも接続先にも影響しない。

## 影響範囲

- **クレート**: `domain`（コマンド実行ポート）、`application`（`run_command` ツール）、
  `infrastructure`（隔離実行アダプタ）、`cli`（結線）。`docker/Dockerfile` / `compose.yml`
  （実行用の隔離環境の設計）
- **不変条件**: **あり** — §2（サンドボックス）に新しい脱出面を作る。任意コマンド実行は
  ファイルツールと質の違う攻撃面（ネットワーク・プロセス・リソース）を持つため、
  ネットワーク遮断・ワークスペース外書き込み不可・タイムアウト・出力上限を設計で担保する。
  **着手前に root がユーザーと設計を確認すること**
- **設定・ドキュメント**: `AGENT_SHELL_*`（有効化・タイムアウト等）、`.env.example`、
  `README.md` §4（ツール表）・§5（サンドボックス）
- **利用者への影響**: 新ツール追加。`ToolSafety` は `Destructive` 扱いとし、
  `read-only` ポリシー（既定）では必ず承認が入る

## 達成条件

- [ ] モデルが `cargo test` 相当のコマンドを実行し、出力（切り詰め済み）を `tool_result` で受け取れる
- [ ] 実行環境からネットワークに出られないことをテストで固定する
- [ ] 実行環境からワークスペース外に書き込めないことをテストで固定する
- [ ] タイムアウトと出力上限が効く（暴走コマンドがループを止めない）
- [ ] 既定の承認ポリシー（`read-only`）で必ず確認プロンプトが入る
- [ ] `security-review-agent` のレビューを通す
- [ ] `make check` が緑

## 優先度の根拠

コーディングエージェントが自分の変更を検証できないのは主要機能の欠落であり、
回避策（人間が毎回実行して結果を転記）のコストが高い（重要度 high）。
他の issue（実 LLM 検証、sub-agent）もこの能力があると検証が楽になるため、
先送りするほど手動検証の手間が積み上がる（緊急度 medium）。

## メモ

- 隔離の実現方式は要設計: 同一コンテナ内での実行は compose 側の隔離（cap_drop 等）を
  流用できるが、ネットワーク遮断は別コンテナ（`network_mode: none`）か
  ネットワーク名前空間の分離が要る。docker socket をマウントしない方針（README §1）と
  両立する方式を選ぶこと
- 許可コマンドのallowlist方式（`make check` など既知のもののみ）から始める案もある。
  攻撃面が大幅に減る代わりに汎用性が落ちる。設計確認時に決める
