# 1 セッションのログファイルが青天井に太るのを止める

`session-log-rotation` から切り出したものです。あちらはディレクトリ内の
**セッション数と古さ**に上限を付けました。1 つのファイルの大きさには効きません。

## As-is（現状）

`agent chat --resume` は同じファイルに追記を続けます。1 セッション 1 ファイルなので、
**同じセッションを再開し続けるかぎりそのファイルは伸び続けます**。

保持ポリシー（`AGENT_SESSION_KEEP` / `AGENT_SESSION_MAX_AGE_DAYS`）はこれを止めません。
再開するたびに mtime が新しくなるので、件数でも日数でも消える側に回りません。
むしろ「よく使っているセッションほど大きく、かつ絶対に消えない」という形になります。

1 ターンの上限は「`AGENT_MAX_ITERATIONS` × `AGENT_MAX_TOOL_OUTPUT_BYTES`」で、
既定では 25 × 32 KB ≈ 800 KB。毎日再開して 10 ターンずつ話す使い方なら、
1 ヶ月で数百 MB に届きます。

効いてくるのは再開のときです。`FileSessionStore::load` は履歴を再生するために
**そのファイルを丸ごと読みます**。再開が重くなる一方で、読み込んだ履歴のほとんどは
最初のターンの圧縮で要約に畳まれます。**読む量は増え続け、使う量は増えません。**

## To-be（あるべき姿）

長く使っているセッションでも、再開にかかる時間とファイルの大きさが頭打ちになる。
古い部分は消えるか別ファイルに移るかして、ユーザーから見て「重くなってきた」がない。

記録として遡りたい分は、消えるにしても**いつ消えるかが分かる**。

## 影響範囲

- **クレート**:
  - `domain` … 再開時に読む範囲を絞るなら `Conversation` 側に整合性の後処理が要る
    （先頭が孤児の `tool_result` にならないこと。`trim_to_budget` に既存の規律がある）
  - `infrastructure` … `session/log.rs`（書く側の分割）、`session/store.rs`（読む側）
  - `cli` … 設定が増えるなら結線
- **不変条件**: **§4 すべての `tool_call` に結果を返す** — 途中から読み始める案・
  古い行を落とす案のいずれも、切り口が `tool_call` と `tool_result` の間に落ちうる
- **設定・ドキュメント**: `.env.example`、`README.md` §3 / §4 / §8、
  `management/docs/architecture.md` §3.2.3
- **利用者への影響**: 案によっては**過去の記録が消える**。`session-log-rotation` で
  入れた「消えるときは分かる」の扱いと揃える

## 達成条件

- [ ] 同じセッションを繰り返し再開しても、再開にかかる時間が伸び続けない
- [ ] 1 セッションが占めるディスクに上限がある、または上限を設定できる
- [ ] 上限は解除できる（記録を全部残したい人がいる）
- [ ] 切り詰め・分割の結果として、孤児の `tool_result` を作らない（不変条件 §4）
- [ ] 消える／移動する場合、それがユーザーに分かる
- [ ] `agent sessions` の id と `--resume <ID>` の関係が壊れない
- [ ] `make check` が緑

## 優先度の根拠

放置すると再開が遅くなりディスクを食うが、**現れるのは同じセッションを長期間
再開し続けた場合だけ**で、`/reset` や新しいセッションで始めれば回避できる（重要度 `medium`）。
`session-log-rotation` でディレクトリ側の歯止めは入っており、実装コストは時期によって
変わらない（緊急度 `low`）。score 5 → P2。

## メモ

- **どの案も §4 に触れます。着手前にどれを採るか決めてください。**
  - **案 A: 再開時に末尾から一定量だけ読む。** 書く側は変えない。読み始めが
    ターンの途中に落ちるので、先頭の孤児 `tool_result` を落とす後処理が要る
    （`trim_to_budget` に既存の規律がある）。**最初のユーザー依頼が落ちる**のが難点で、
    それは圧縮が最も守ろうとしているものでもある
  - **案 B: 再開のたびに新しいファイルを開き、前のファイルを参照する。**
    1 セッションが複数ファイルになる。`session-persistence-and-resume` で決めた
    「1 セッション 1 ファイル」を崩すので、id と `--resume` の対応をどうするか決める必要がある
  - **案 C: 書く側で古い部分を切り詰める。** 追記専用という性質を捨てることになる。
    ログの価値の大半は「消えない」ことなので、これは最後の手段
- 案 A を採るなら、**最初のユーザー依頼だけは別に保持する**手はある
  （ファイル先頭の数 KB は一覧の preview のために既に読んでいる）
- 圧縮が「どこまでを畳んだか」をログに記録しておけば、再開時にそこから読み始められる。
  記録の形を変えるので `SCHEMA_VERSION` を上げる
