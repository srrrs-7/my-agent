# sub agent 機能（モデルが子エージェントにタスクを委譲できるようにする）

## As-is（現状）

エージェントは単一ループ・単一履歴で動く。大きな調査（多数のファイル読み・検索）を
させると中間結果が履歴予算（`AGENT_MAX_HISTORY_BYTES`）を圧迫し、刈り込みで
肝心の文脈から消えていく。ユーザーは大きなタスクを自分で小さく割って、
順番に依頼するしかない。

## To-be（あるべき姿）

モデルがサブタスクを子エージェントに委譲できる。子は自分の履歴の中で調査・作業し、
**要約だけ**を親に返す。親の履歴は要約分しか消費しないので、ユーザーは
「crates 全体を調査して改善案を出して」のような大きなタスクを一度で頼める。

## 影響範囲

- **クレート**: `application`（`spawn_agent` ツール、子 `AgentLoop` の組み立てと実行、
  深さ制限）、`domain`（必要なら子仕様の値オブジェクト、イベントの階層表現）、
  `cli`（子の活動の描画。インデントや色分け）
- **不変条件**: §1 が設計論点 — ツールが `AgentLoop` を参照すると構築が循環する
  （ループ→レジストリ→ツール→ループ）。遅延注入か factory で解決する必要があり、
  `application` を tokio 非依存に保ったまま実現できるかを先に設計する。
  §3・§4（ツール失敗の扱い・全呼び出しへの応答）は子ループにもそのまま適用
- **承認**: 子のツール実行も**同じ** `ApprovalGate` を通すこと。子経由で承認を迂回できたら
  ゲートの意味がない
- **設定・ドキュメント**: `AGENT_MAX_SUBAGENT_DEPTH` 等、`.env.example`、`README.md` §4
- **利用者への影響**: 新ツール追加。既存の動作は変わらない

## 達成条件

- [ ] モデルが `spawn_agent`（名称は要検討）で子ループを起動し、子の最終回答のみを
      `tool_result` で受け取れる
- [ ] 子の履歴・ツール出力が親の履歴に混入しない（親の消費は要約分のみ）ことをテストで固定
- [ ] 深さ上限・子の反復上限が効き、子の暴走が親の予算とは独立に止まる
- [ ] 子のツール呼び出しが承認ゲートを通る（`read-only` ポリシーで子の書き込みにも確認が入る）
- [ ] 子の失敗（反復切れ・プロバイダ障害）は `is_error` 付き `tool_result` として親に返り、
      親のループは継続する
- [ ] `domain-specialist-agent` に設計（循環の解き方）を確認してから実装する
- [ ] `make check` が緑

## 優先度の根拠

コンテキスト管理はエージェントループの中心課題で、ゴール 1（ループエンジニアリング）に
直結する（重要度 high）。ただし単一ループが実モデルで機能することの検証
（2026-08-14_verify-against-a-real-llm, P0）が先であり、今やらないと損をする性質ではない
（緊急度 low）。

## メモ

- 小さいローカルモデルは委譲の判断自体が苦手な可能性がある。実 LLM 検証の結果を見てから
  ツール description の書き方を決める
- 並列に複数の子を走らせるのは第 2 段階。まず直列 1 子で成立させる
- コンテキスト圧縮（2026-08-14_context-compaction-by-summarization）とは補完関係:
  圧縮は「溢れたら要約」、sub agent は「最初から溢れさせない」
