# コスト／レイテンシベースのルータと自動フェイルオーバー

## As-is（現状）

ルーティングは `static`（常に既定プロバイダ）と `model-prefix`（`-m cloud/model` で手動選択）
の 2 つだけ。プロバイダが落ちているとリトライの後にそのターンが失敗し、ユーザーが手で
`-m` を切り替えるしかない。タスクの性質（要約なら安いモデルで十分、など）に応じた
自動の使い分けもできない。

## To-be（あるべき姿）

複数プロバイダを設定しておけば、タスク種別・コスト・レイテンシに応じて自動で
使い分けられる。片方の障害時はもう片方に自動で切り替わり、ユーザーは障害を意識しない。
どのプロバイダがなぜ選ばれたかは `-v` で確認できる。

## 影響範囲

- **クレート**: `infrastructure` のみ（`llm/routing.rs` に新ルータ実装、
  ヘルス状態の追跡、`llm/factory.rs` と `config/` の拡張）。
  `LlmRouter` の seam と `RequestMetadata`（`task_kind` / `hints`）は既にあるため、
  `domain` / `application` / 既存プロバイダには原則手を入れない。
  `RouteDecision` で表現力が足りるかだけ要確認
- **不変条件**: なし
- **設定・ドキュメント**: `AGENT_ROUTER` の値追加（`failover` / `cost` など）、
  プロバイダ別メタデータ（コスト・優先順位）の環境変数、`.env.example`、README §6・§8
- **利用者への影響**: なし（既存の `static` / `model-prefix` はそのまま。追加のみ）

## 達成条件

- [ ] フェイルオーバー: 第一候補が落ちているとき、同一リクエストが次候補で成功する
      （モックでテスト。復帰後は第一候補に戻ることも確認）
- [ ] `TaskKind::Summarize` / `Classify` を指定プロバイダに向けるルーティングが
      設定だけで組める
- [ ] ルーティング判断が理由付きで trace（`-v`）に現れる
- [ ] 実装は `LlmRouter` の追加のみで、`AgentLoop` と既存プロバイダのコードに変更がない
      （変更が必要になったら seam の設計不備として先に相談）
- [ ] `make check` が緑

## 優先度の根拠

当初からの計画機能であり、そのために `LlmRouter` / `RequestMetadata` の seam を
先行して用意してある（重要度 high）。ただし価値が顕在化するのは複数プロバイダ運用を
始めてからで、現状の単一 Ollama 構成では急がない（緊急度 low）。

## メモ

- コスト計算に価格表を持つなら、その保守方法（ハードコードか設定か）を先に決める。
  最初は「優先順位リスト + ヘルスチェックによるフェイルオーバー」だけで十分価値がある
- コンテキスト圧縮 issue の要約リクエストがこのルータの最初の実利用者になれる
  （安いモデルへ逃がす）
