# システムプロンプトを外部から注入できるようにする

## As-is（現状）

システムプロンプトは `build_system_prompt`（`crates/application/src/agent/prompt.rs`）に
ハードコードされた文面から組み立てられ、外から変更する手段がない。
唯一の注入点はプロジェクト指示ファイル（`AGENTS.md` 等）だが、これは既定プロンプトへの
**追記**であり、全体の差し替えや作業ルールの調整はできない。

プロンプトを試行錯誤したいユーザー（このリポジトリのゴール 1「ループエンジニアリング」の
実践者）は、1 回の変更ごとに Rust コードを書き換えて再ビルドするしかない。

## To-be（あるべき姿）

ユーザーが再ビルドなしにシステムプロンプトを変えられる。

- **差し替え**: 用意したファイル（または環境変数）の内容で既定プロンプト全体を置き換える
- **追記**: 既定プロンプトを保ったまま、追加の指示を末尾に足す

`.env` の設定だけでプロンプト実験のイテレーションが回り、
CLI フラグで 1 回の実行だけ変えることもできる。

## 影響範囲

- **クレート**: `application`（`AgentLoopConfig` に差し替え／追記のフィールドを追加し、
  `loop_runner.rs` の組み立てで解釈。層の純粋性は保たれる — 読み込みは外側の責務）、
  `infrastructure`（`config/` に環境変数の読み取り）、
  `cli`（`--system-prompt-file` / `--append-system-prompt` フラグ、`composition.rs` で
  ファイル読み込みと結線）
- **不変条件**: なし。ただし 2 点を設計メモに明記する
  - サンドボックスはコードで強制されており（§2）、プロンプトを差し替えても
    ツールがワークスペース外に出られるようにはならない（プロンプトは防御層ではない）
  - 注入ファイルの読み込みは**起動時に操作者（人間）が行う**ものであり、モデルのツール
    経由ではないため、ワークスペース外のパスを許してよい
- **設定・ドキュメント**: `AGENT_SYSTEM_PROMPT_FILE` / `AGENT_APPEND_SYSTEM_PROMPT`（名称は
  実装時に確定）、`.env.example`、`README.md` §4（context の節）・§8（変数表）
- **利用者への影響**: なし（追加のみ。未設定なら現行と同一のプロンプト）

## 達成条件

- [ ] 環境変数（ファイルパス指定）で既定プロンプト全体を差し替えられる
- [ ] 環境変数で既定プロンプトの末尾に追記できる（プロジェクト指示ファイルとの順序を
      README に明記する）
- [ ] CLI フラグで同じことができ、環境変数より優先される
- [ ] 差し替えモードでもツール呼び出しが機能する（ツール定義はプロンプトと独立に
      渡っていることを E2E で確認）
- [ ] 指定ファイルが存在しない・読めない場合は起動時に明確なエラーで落ちる
      （黙って既定にフォールバックしない）
- [ ] 未設定時の送出プロンプトが現行と byte 単位で同一（退行テスト）
- [ ] `.env.example` と `README.md` §8 が更新されている
- [ ] `make check` が緑

## 優先度の根拠

回避策（コード編集 + 再ビルド）はあるが、プロンプト実験の主目的に対して高コスト
（重要度 medium）。P0 の実 LLM 検証では小さいローカルモデル向けにプロンプトの調整が
必要になる見込みが高く、先にこれがあると検証のイテレーションが速くなる（緊急度 medium）。

## メモ

- 実装方針の候補: `AgentLoopConfig` に `system_prompt: SystemPromptSource` 的な enum
  （`Default` / `Replace(String)` / `DefaultWith { appended: String }`）を持たせると、
  `build_system_prompt` の呼び出し側の分岐が明確になる
- 差し替えモードでは環境情報（ワークスペースパス・日付・ディレクトリ概要）も消える。
  それを差し替え文面から参照できるプレースホルダ（`{workspace}` 等）を入れるかは
  第 2 段階でよい。まず素の差し替えを成立させる
- プロンプトはプロバイダ側キャッシュのため実行内で安定している必要があるが、
  現行どおり run の先頭で 1 回組み立てる構造なら自然に満たされる
