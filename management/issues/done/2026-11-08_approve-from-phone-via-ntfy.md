# 承認待ちの通知に、スマホから承認・拒否で答えられるようにする（ntfy の返信を外向きに購読）

## As-is（現状）

承認待ちの通知（Webhook）はスマホに届きますが、答えるには端末の前に戻るしかありません。
通知を見ても、エージェントは人が戻るまで止まったままです。

## To-be（あるべき姿）

- 承認待ちの ntfy 通知に「承認」「拒否」の操作が付き、押すとその場でエージェントが続行する
  （拒否ならモデルが方針を変える）
- 端末で先に答えれば端末の答えが採られ、遅れて届いたスマホからの返事は無視される。逆も同じ
- 一度使った返事、別の承認に宛てた返事、推測で作った返事は効かない
- 受信のためにポートを開ける必要がない（エージェントから ntfy へ外向きに購読する）
- 設定しなければ今と同じ

## 影響範囲

- **クレート**:
  - `infrastructure` … `notify/`（返信トピックの購読 — 長くつなぎっぱなしの外向き HTTP、
    承認ごとの 1 回限りのトークン、通知への操作ボタン）、`config/`
  - `domain` … 遠隔の返事を受け取る境界（`Notifier` は今は送るだけ）、
    `NotificationEvent::ApprovalPending` にトークン（相関 ID）
  - `cli` … `approval.rs`（端末の入力と遠隔の返事の早い方を採る）、`input.rs`（下のメモ）、
    `composition.rs`、`doctor`
  - `test-support` … 今のモックは決まった応答を返すだけ。**通知を受けた後で返信を流す**
    （購読ストリームに後から書く）モックが要る
- **不変条件**:
  - §3 — 遠隔の失敗や購読切れは、端末での待ちに戻るだけ。ツール失敗にも実行失敗にもしない
  - §5 — テストは生 TCP のモックで
  - §1 — 購読とタイマーは `infrastructure` に置く
- **設定・ドキュメント**: `README.md` §3（通知）・§8（返信トピックなどの変数）。
  「誰が承認できるか」という脅威モデルを README に書く
- **利用者への影響**: 既定は無効。破壊的変更なし

## 優先度の根拠

離席中に承認できる便利さで、通知を見て端末に戻る回避策がある（重要度 `medium`）。
ただし外部から承認できる経路を新しく作るので、セキュリティ面の設計は重い。承認内容の外部送信の
扱いがユーザー確認中で、秘密の保護（A）と取り消せる入力待ち（Ctrl-C の issue）を前提にする。
待つほど前提が揃い、コストは増えない（緊急度 `low`）。score 5 → P2。

## メモ

- **設計確認中。承認内容（引数）の外部送信の扱いはユーザーに確認中。**
- 調査で分かったこと（2026-11-08, issue-agent）:
  - **1 回限りのトークンが防げるのは、返信トピックへの当て推量と再送だけ。** トークンを通知の
    ボタンに載せる以上、**通知トピックを読める人は誰でもそのトークンで承認できる。** ntfy.sh の
    公開トピックは名前を知っていれば誰でも購読できる（README §3 に既に注意書きがある）。
    アクセス制御つきの自前サーバか、ntfy のアクセストークンを前提にするかを決める
  - **入力待ちが取り消せない。** `input.rs` の `prompt_line` は `spawn_blocking` で stdin を読むため、
    遠隔の返事が先に来て future を捨てても、読み取りスレッドは残って**次に打った 1 行を飲み込む**。
    Ctrl-C の issue と同じ問題なので、そちらで取り消せる入力待ちを作って共有する
  - 引数を載せずに承認させると、スマホでは中身を見ずに承認することになる。載せるなら A の伏せ字を通す。
    `domain/src/ports/notify.rs` には「引数は意図的に載せない」理由が書いてあり、変えるならそこも直す
  - 非対話の `agent run` は今、確認が要る呼び出しを自動で拒否する。遠隔承認を待つようにすると
    `run` の意味が変わる。対象にするかを決める
  - 「以降すべて許可（`a`）」を遠隔から許すかを決める

### 設計確認の結論（2026-11-08 domain-specialist → root 決定）

- **なりすまし対策の本質は「通知トピックを誰が読めるか」**。ntfy の標準アプリのボタンは固定文字列を送るだけなので、承認ごとの HMAC は 1 回限りトークン以上に何も守らない（採らない）
- v1 必須: ntfy アクセストークン（無ければ起動失敗）+ **起動時に匿名で通知トピックが読めないこと・返信トピックに匿名で書けないことを実際に試して実証**（通らなければ起動失敗。§2「黙って弱くならない」の承認版）。承認ごとトークンは 128bit 以上（/dev/urandom）、定数時間比較・1 回で破棄・期限付き
- ボタンに載せる書き込みトークンは購読用と分けることを推奨（同一なら起動時に警告）
- **新ポート `RemoteApprover`**（domain、Null 実装は解決しない future）+ ntfy 実装は infrastructure。競合は `CliApprovalGate::authorize` の「人に聞くと決まった後」で `tokio::select!`。装飾子にしない（承認要否の判定が 2 箇所になる）。トークン等は infrastructure 内に閉じる。`NotificationEvent` に引数・トークンを足さない
- detail は cli の純粋関数で「伏せ字 → 切り詰め」の順、上限付き。遠隔有効時は `approval_pending` の代わりに `remote.ask` が通知（二重に鳴らさない）
- 遠隔側の失敗・購読切れ・不正な返事は warn して端末待ちを続ける（拒否にしない）。Ctrl-C は既存の plan ごと drop で正しく動く
- 購読は通知の前に開始（または since 指定）。長いポーリングには全体 timeout の無い別 client
- root 決定: 自由文の拒否理由は v1 で削る（偽造理由がプロンプトインジェクションになる）。遠隔有効時は `AGENT_NOTIFY_EVENTS` に関係なく承認待ちを送る。**依存承認は端末のみ**（スマホには「端末で待っています」通知だけ）。「a（以降すべて）」は遠隔不可。時間切れはトークン失効のみ（自動拒否しない）。非対話 `run` は対象外のまま。safety 区分による制限はしない
- ntfy トークンと返信トピックを Redactor の秘密に加える。README に脅威モデル（承認できるのは通知トピックを読める人、ntfy サーバは信頼前提）
