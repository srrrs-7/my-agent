# LLM 要約によるコンテキスト圧縮

## As-is（現状）

履歴が予算（`AGENT_MAX_HISTORY_BYTES`）を超えると、古いメッセージから**丸ごと破棄**される。
長い chat セッションでは序盤に決めた方針や調査結果をモデルが忘れ、同じ質問を繰り返したり
前の決定と矛盾する提案をしたりする。ユーザーは文脈を説明し直すか `/reset` で
仕切り直すしかない。

## To-be（あるべき姿）

履歴が予算に近づくと、古いターンが LLM 生成の要約 1 メッセージに置き換わる。
長いセッションでも「何を決めたか・何を調べたか」の要点が維持され、
ユーザーが文脈を言い直す頻度が下がる。

## 影響範囲

- **クレート**: `application`（圧縮ユースケースとループへの組込み。
  `TaskKind::Summarize` は定義済みで、要約リクエストに載せる）、
  `domain`（`Conversation` に区間を要約で置換する操作）、
  `cli`（圧縮発生の可視化。`AgentEvent::HistoryTrimmed` の拡張か新イベント）
- **不変条件**: §4 に隣接 — 要約対象区間の切り出しは `tool_call` / `tool_result` の対を
  跨いで孤児を作ってはならない。`trim_to_budget` と同じ規律をテストで固定する
- **設定・ドキュメント**: 発火閾値（`AGENT_COMPACT_*`）、`.env.example`、README §4
- **利用者への影響**: 既定で有効にするかは要検討（要約 1 回分の追加コストとトークンが発生する）

## 決めたこと

### 発火閾値は設けず、「刈り込みが起きる条件」と同一にした

計画では `AGENT_COMPACT_*` に閾値を持たせる想定でしたが、**設定項目を 1 つ減らして
「内容が失われる瞬間に圧縮する」**としました。刈り込みは常にバックストップとして
後段に残るので、早めに発火させる利点が小さい一方、閾値は説明・文書化・テストの
対象が増えます。設定は `AGENT_COMPACT`（既定 true）と `AGENT_COMPACT_KEEP_RECENT`
（既定 12）の 2 つだけです。

### 既定で有効にした（issue の「要検討」への回答）

追加コストは 1 リクエストですが、それが発生するのは**内容が失われる瞬間だけ**です。
削除が最初に消すのは最も古いメッセージ、つまりユーザーが要件を述べた行であり、
その損失は「動かない」ではなく「決着した話を蒸し返す」という追跡困難な形で現れます。
失敗しても従来の削除に落ちるだけなので、下振れは限定的です。`AGENT_COMPACT=false`
で従来動作に戻せます。

### 要約リクエストは元のメッセージ列ではなく平坦化したテキスト 1 通

ツール定義を宣言しないリクエストに `tool_call` ブロックを載せた場合の扱いは
プロバイダ間で一致していません。これは**セッションが既に苦しいときに必ず通らなければ
ならない**唯一のリクエストなので、最も互換性の高い形にしました。副次的に、
ツール出力だけを切り詰めてユーザー発言を無傷で送ることが可能になります。

### 要約は `user` ロールで先頭に入る

プロバイダは会話が user で始まることを期待し（Anthropic は明示的に要求）、圧縮後は
要約がその先頭になります。assistant で入れるとモデルが「自分が言ったこと」＝検証済みの
推論として扱ってしまう点も避けたい挙動です。本文には「これは記録であって新しい依頼では
ない」と明記しています（要約に*答えて*しまうのを防ぐため）。

## 残した問題

`trim_to_budget` は先頭の `tool` メッセージだけを避けており、**先頭が assistant に
なる可能性が残っています**。Anthropic は最初のメッセージが user であることを要求するため
拒否される可能性が高いのですが、実エンドポイントで未検証です。圧縮が有効なら先頭は
要約（user）になるため主経路では顕在化しません。別 issue
（`2026-08-14_history-head-must-be-a-user-message.md`）に切り出しました。

## 優先度の根拠

長セッションの品質改善であり、回避策（`/reset`・再説明）が存在する（重要度 medium）。
現状の主用途は短い単発タスクで、破綻が頻発しているわけではない（緊急度 low）。

## メモ

- 要約プロンプトは「決定事項・未解決の論点・変更したファイル」を残すよう指示する。
  散文の再現ではなく作業状態の保存が目的
- sub agent 機能（2026-08-14_sub-agent-support）と補完関係:
  圧縮は「溢れたら要約」、sub agent は「最初から溢れさせない」
