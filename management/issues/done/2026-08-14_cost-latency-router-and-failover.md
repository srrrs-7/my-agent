# ローカル優先のハイブリッド実行（タスク種別ルーティングとクラウド障害時の自動フェイルオーバー）

> **2026-11-08 具体化。** 旧題「コスト／レイテンシベースのルータと自動フェイルオーバー」。
> 依頼「B. ローカル優先のハイブリッド実行」を新しく起票せず、この issue に統合した。
> 依頼の 3 点（タスク種別での振り分け、自動フェイルオーバー、`-v` での可視化）はすべて元の
> 達成条件に含まれていたため。コスト・レイテンシに基づく自動選択は範囲外にした（メモ参照）。
> ファイル名は規約どおり変えない。

## As-is（現状）

複数プロバイダ（`AGENT_PROVIDERS=local,cloud`）は設定できますが、ルータは `static`（常に既定）と
`model-prefix`（`-m cloud/...` で手で選ぶ）の 2 つだけです。

- ローカル（Ollama）とクラウドを併用しても、「要約だけローカルに回す」といった使い分けができない。
  履歴の圧縮の要約リクエストは本体と同じプロバイダに行く。要約は畳む範囲の履歴全体を送るので、
  セッションの中で最も大きいリクエストの 1 つになる
- クラウドが落ちると、リトライの後にそのターンが失敗する。手で `-m` を切り替えるしかない
- `-v` にはモデル名は出るが、どのプロバイダに振られたか・なぜかは出ない（判断理由は
  `RUST_LOG=debug` の tracing にしか出ない）。圧縮の要約がどこで処理されたかはどこにも出ない

## To-be（あるべき姿）

- 要約・分類（`TaskKind::Summarize` / `Classify`）はローカル、本体のループはクラウド、という
  振り分けを設定だけで組める
- クラウドの障害時は自動でローカルに切り替わり、ターンは失敗しない。クラウドが戻れば、
  次のリクエストからクラウドに戻る
- どのリクエストがどこに振られたか、フェイルオーバーが起きたかが `-v` で見える
- 既存の `static` / `model-prefix` の設定はそのまま動く

## 影響範囲

- **クレート**:
  - `infrastructure` … `llm/routing.rs`（タスク種別のルータ）、フェイルオーバーとヘルス状態の追跡、
    `llm/factory.rs`、`config/`。今は `Retry(Route(...))` の順で積んでおり、ルータは宛先を 1 つしか
    返さない（`RouteDecision`）。フェイルオーバーをルータで表すか、合成プロバイダで表すか、
    リトライの内側と外側のどちらに置くかを決める
  - `cli` … `-v` の表示（`render.rs`）
  - `domain` … **表示の方式次第。** 今の `-v` は tracing ではなく `TerminalRenderer` の詳細表示で、
    ルータは `EventSink` を持たない。理由やフェイルオーバーを `-v` に出すには、`ChatResponse` か
    `AgentEvent` に経路の情報を足すことになりうる
- **不変条件**: なし。§1 に注意 — ヘルス追跡や待ちのタイマーは `infrastructure` に置く
- **設定・ドキュメント**: `AGENT_ROUTER` の値の追加、タスク種別ごとの宛先とフェイルオーバーの順序を
  決める変数（既定値を持たせる）、`README.md` §6（LLM ルーティング）・§8（複数プロバイダとルーティング）。
  `.env.example` は必須項目が変わらないので触らない
- **利用者への影響**: なし（既存の `static` / `model-prefix` はそのまま。追加のみ）

- [x] 復帰後は第一候補に戻る
- [x] ストリーミングで本文を流し始めた後の失敗では切り替えない（出力が二重になるため）。挙動をテストで固定する

- [x] 既存の `static` / `model-prefix` に退行がない

## 優先度の根拠

当初からの計画機能で、そのために `LlmRouter` / `RequestMetadata` の seam を先に用意してある
（重要度 `high`）。

**2026-11-08 に緊急度 low → medium、P2 → P1 へ変更。** 起票時に low とした前提は
「価値が出るのは複数プロバイダ運用を始めてからで、単一 Ollama 構成では急がない」だったが、
ユーザーがローカル＋クラウドの併用とこの issue の実装を決めたため、その前提がなくなった。
プロンプトキャッシュ・評価ハーネスと LLM の経路に手を入れる作業が続くので、`Retry(Route)` の
積み順とフェイルオーバーの位置を先に決めるほど後の手戻りが少ない。score 8 → P1。

## メモ

- **設計確認中。**
- 範囲外（第 2 段階）: コスト・レイテンシに基づく自動選択。必要になったら別 issue に切り出す。
  価格表を持つなら保守方法（ハードコードか設定か）を先に決める（起票時のメモ）
- 調査で分かったこと（2026-11-08, issue-agent）:
  - **`TaskKind::Classify` は domain に定義があるだけで、発行するコードがない。** 振り分けの設定は
    作れても、効くのは呼び出し元ができてから
  - **Ollama 側のコンテキスト長（要確認）。** Ollama は既定のコンテキスト長が小さく、超えた分を
    黙って切り捨てることがある（モデル・バージョン依存）。要約リクエストは畳む範囲の履歴全体を
    送るので、ローカルに振ると**要約が黙って欠けうる。** コンテキスト長の指定か、要約の入力上限が要る
  - ローカルへのフェイルオーバーは品質の低下を伴う（小さいモデルはツール呼び出しが不安定でありうる —
    `verify-against-a-real-llm` の確認待ち）。`-v` なしでも警告 1 行を出すかを決める
  - `RoutingProvider::capabilities()` は全候補の積集合。ローカルを候補に入れると、クラウドにしかない
    能力が広告から消える
