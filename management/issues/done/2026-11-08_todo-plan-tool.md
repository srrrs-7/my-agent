# モデルが作業計画（TODO）を書いて更新し、端末に表示できるようにする

## As-is（現状）

複数ステップの作業で、モデルの計画は散文の中にしかありません。ユーザーは今どこまで進んだかを、
端末に流れるツール活動から推測するしかありません。

長いタスクで履歴が圧縮されると、最初に立てた計画は要約に畳まれ、**モデル自身が残りの手順を
見失うことがあります**（圧縮で無傷に残るのはユーザー発言だけ）。`agent chat --resume` で再開しても、
計画は形として残っていません。

計画をファイルに書かせる回避策はありますが、既定の承認ポリシー（`read-only`）では更新のたびに
書き込みの確認で止まります。

## To-be（あるべき姿）

- モデルが計画（手順と、未着手／作業中／完了の状態）を書き、進むたびに更新できる
- 更新のたびに端末（stderr）に今の計画が表示され、どこまで進んだかが一目で分かる
- 履歴が圧縮・刈り込みされても、モデルは常に最新の計画を見ている
- `agent chat --resume` で再開すると、中断時点の計画が戻る。`/reset` で消える
- 計画の更新では承認を求められない（ワークスペースを変えないため）

## 影響範囲

- **クレート**:
  - `domain` … 計画の値（項目と状態。「作業中は 1 つまで」のような規則を持つならここ）、
    `AgentEvent` に計画更新のイベント
  - `application` … `tools/` に計画ツール。**ツールは `Session` に触れない**（`run` に
    `&mut Session` が渡り、ツールは構築時にレジストリへ固定される）ので、計画をどこに持つかを
    設計する。圧縮後もモデルに見せる仕組み（`agent/compaction.rs` / `build_request`）
  - `infrastructure` … `session/store.rs` の再生で計画を復元する。ログの最後の計画ツール呼び出しから
    導くなら記録の形式は変わらない。専用の行を書くなら `SCHEMA_VERSION` を上げる
  - `cli` … `render.rs`（表示）、`composition.rs`（登録）、`commands/chat.rs`（`/reset` で消す、
    必要なら `/plan`）
- **不変条件**:
  - §4 — 計画ツールを `ReadOnly` に分類すると、同じターンの読み取り系ツールと**並列実行される**
    （`AGENT_PARALLEL_READ_TOOLS`）。同じターンに更新が 2 回来たときの順序を決める必要がある
    （例: 毎回全体を置き換える意味にする）
  - §1 — 共有状態が要っても `application` に tokio を入れない（std の同期プリミティブで足りる）
  - §3 — 規則に反する計画は `is_error` の `tool_result` で返し、ループは続ける
- **設定・ドキュメント**: `README.md` §4（tools の表、loop・圧縮の節）、
  `management/docs/architecture.md` §4（コンテキストエンジニアリング）、
  system プロンプト（`agent/prompt.rs`）でのツールの使い方の案内
- **利用者への影響**: ツールが 1 つ増える。既存の動作は変わらない

## 優先度の根拠

長いタスクで計画が圧縮に負けるのは、ループとコンテキスト構築（ゴール 1）そのものの穴で、
ファイルに書かせる回避策は書き込み承認のたびに止まる（重要度 `high`）。計画をリクエストのどこに
差し込むかがプロンプトキャッシュの効き方を決め、圧縮・セッションログの規則にも絡むため、
周辺が固まるほど後付けが重くなる（緊急度 `medium`）。score 8 → P1。

### 設計確認の結論（2026-11-08 domain-specialist → root 決定）

- **真実は会話**: 計画 =「成功した最新の `todo_write` 呼び出しの引数」（毎回丸ごと置換）。ツールは検証して整形を返すだけで状態を持たない（`application/src/tools/plan/`）。射影 `latest_plan(&[Message])` は application。`Session.plan` はキャッシュで、結果 push 直後に最新ターンだけ射影して更新。消せるのは空リストの `todo_write` だけ
- `Plan` / `PlanItem` / `PlanStatus{Pending,InProgress,Completed}` は domain の値オブジェクト（`model/plan.rs`）。不変条件: in_progress は**最大 1**、項目上限 20、各項目は空でない 1 行・上限 200 バイト。違反は黙って直さず構造化エラーで拒否
- **注入はしない**のが平常時（tool_result が計画を運ぶ）。`fit_history` が履歴を短くした直後に、未完了項目があれば user ロールの「エージェントのメモ」を **1 回だけ** push + 記録（ピン）。本文に「ユーザーの発言ではない」「後の `todo_write` と直前のユーザー発言が優先」と明記。キャッシュは短縮時点で既に無効なので追加コストなし
- 使わない注入先: system プロンプト / PromptBuilder / ContextProvider（キャッシュを壊す・FixedPromptBuilder で消える）、リクエストだけの一時ブロック、`Role::Tool` 内の Text（OpenAI 互換で消える）、毎イテレーションの追記
- 表示: `AgentEvent::PlanUpdated{plan}`（キャッシュが変わったときだけ）を stderr にチェックリストで描画
- 再開: `Session::resumed(id, conversation)` で全履歴から射影して復元
- 安全分類は `ReadOnly`（並列でも結果が要求順なので「最後が勝つ」で決まる）
- composition 登録と README §4 更新を忘れない（合成ルートにテストがない）

- 2026-11-08 完了。設計からの差分: (1) 計画が残っている間は fit_history の予算からメモの大きさを差し引く（メモで再び予算超過→毎回刈り込み、を防ぐ）。(2) メモは「最新の todo_write も同一メモも履歴に見えないとき」だけ追記（keep_recent の下限で予算超過が続くと毎イテレーション追記される問題をテストで発見）。/plan コマンド追加。既知: 要約役がメモを user 発言として要約しうる（後続の短縮で再ピンされるので影響は限定的）
