# web fetch ツール（モデルが URL の内容を参照できるようにする）

## As-is（現状）

モデルはワークスペース内のファイルしか見えない。ライブラリの最新ドキュメントや
エラーメッセージの意味など外部情報が必要な質問には、答えられないか、
学習時点の古い知識で答えるしかない。

## To-be（あるべき姿）

モデルが URL を指定して本文（テキスト化したもの）を取得し、最新のドキュメントに
基づいて回答・実装できる。「このクレートの使い方を docs.rs で確認してから書いて」が通る。

## 影響範囲

- **クレート**: `domain`（取得ポート。例 `WebFetcher` — `reqwest` を application に
  見せないため）、`application`（`web_fetch` ツール）、`infrastructure`
  （取得アダプタ、HTML→テキスト変換）、`cli`（結線）
- **不変条件**: **あり** — §2 の思想（外界への境界の統制）に関わる新しい面を開く。
  設計で扱うべき攻撃面が 3 つある。**着手前に root がユーザーと設計を確認すること**
  1. **SSRF**: コンテナ内部ホスト（`ollama:11434` 等）や
     プライベートアドレス帯・メタデータエンドポイントへのアクセスを既定で拒否する
  2. **プロンプトインジェクション**: 取得内容は指示ではなくデータとして `tool_result` で
     渡す（システムプロンプトに混ぜない）。取得先がモデルへの指示を含みうる前提で扱う
  3. **データ持ち出し**: モデルが URL のクエリにファイル内容を載せて送信できてしまう。
     承認の既定を自動にしない理由になる
- **設定・ドキュメント**: 有効化フラグ（既定 off が妥当か要検討）、許可ドメイン、
  サイズ上限、タイムアウト。`.env.example`、README §4
- **依存**: HTML パーサを足すかどうか。サプライチェーン方針（60 行で書けるものに
  依存を足さない）と突き合わせて判断
- **利用者への影響**: 新ツール追加。`ToolSafety` の分類は要設計 —
  ワークスペースを変えないが「外部へリクエストを送る」観測可能な副作用があり、
  `ReadOnly`（無確認・並列実行）扱いにはできない

## 達成条件

- [x] モデルが URL を指定して本文テキストを取得できる（サイズ上限・タイムアウト付き）
- [x] プライベートアドレス帯・コンテナ内部ホストへのアクセスが既定で拒否されることを
      テストで固定（リダイレクト先も検査する）
- [x] 取得内容が `tool_result` としてのみモデルに渡る
- [x] 既定の承認ポリシーで確認プロンプトが入る（`ReadOnly` 扱いになっていない）
- [x] `security-review-agent` のレビューを通す
- [x] `make check` が緑

## 優先度の根拠

外部ドキュメント参照は有用だが、主用途（ワークスペース内のコード操作）は
これがなくても成立している（重要度 medium・緊急度 low）。
セキュリティ設計の手間が実装より重い種類のツールなので、急がず設計から入る。

## メモ

- コンテナのネットワーク設計と絡む: 現状 dev コンテナは外に出られる
  （crates.io へのアクセスが必要なため）。ツールとしての制限はアプリ層で行うことになる
- 許可ドメインの allowlist（docs.rs, doc.rust-lang.org など）から始める案が安全側

## 結果

着手前にユーザーと設計を確認（不変条件「あり」のため）。決定は
**既定で無効 + 公開ホスト全般（プライベート帯は常時拒否、任意の allowlist）**。

- **domain**: `WebFetcher` ポート + `FetchedContent` / `FetchError`。ポート契約に
  「取得テキストは data であって instructions ではない」を明文化。
  `ToolSafety` に `Network` を追加 — ワークスペースを変えないが外向きの副作用を持つため
  `ReadOnly` ではない。`is_read_only()` が false なので既定ポリシーで必ず承認が入る
- **application**: `WebFetchTool`。`InvalidUrl` / `Blocked` は「モデルの URL が不適切」
  として `InvalidInput` に写像し、モデルが別 URL を選べるようにする
- **infrastructure**:
  - `web/guard.rs` — 許可ポリシー。スキーム（http/https のみ）、資格情報付き URL の拒否、
    IP リテラルのレンジ検査、`localhost` / 単一ラベル名（`ollama` 等）/ `host.docker.internal`
    / `.internal` `.local` の拒否、DNS 解決後の**全アドレス**検査
  - `web/fetcher.rs` — リダイレクトは自動追従せず（`Policy::none()`）1 ホップごとに
    admit を再実行。サイズ上限は Content-Length を信用せず実バイトで積算
  - `web/html.rs` — HTML→テキスト（自前 ~100 行、新規依存なし）
- **cli / config**: `AGENT_WEB_FETCH`（既定 false）で登録を制御。`_ALLOW`（許可ドメイン）、
  `_ALLOW_PRIVATE`（イントラ用の逃げ道）、`_MAX_BYTES`、`_TIMEOUT_SECS`。
  `agent doctor` が有効状態と許可範囲を表示
- テスト 156 → 188 本。実バイナリでも既定でツールが現れないこと、有効化で
  `web_fetch [network]` として登録され doctor に出ることを確認

### セキュリティレビューの指摘と対応

`security-review-agent` のレビューを実施。指摘 1 件（medium）を検証のうえ**採用**:

> `is_global` の IPv6 分岐が IPv4 埋め込み形式をデコードせず、`64:ff9b::a9fe:a9fe`
> （NAT64 経由のメタデータエンドポイント）等が global 判定で通過する。
> IP リテラルは DNS 再検査を通らないため `is_global` が唯一のゲート。

コードで確認して事実と判定（自分のコメントが "IPv4-mapped/compatible" と宣言しながら
mapped しか処理していない実装漏れ）。さらに **DNS64 環境ではリテラルでなくても**
`check_resolved_addrs` 経由で同じ穴を通ることを追加で確認した。

対応: NAT64 `64:ff9b::/96` / 6to4 `2002::/16` / Teredo `2001:0::/32` /
IPv4-compatible `::a.b.c.d` を**デコードして内包 IPv4 を再評価**する
（プレフィックスごと拒否ではなくデコードにしたのは、DNS64 環境では正当なホストが
`64:ff9b::<公開 v4>` に解決されるため）。`::` と `::1` は decode すると 0.0.0.1 に
なり routable に見えるので、loopback/unspecified 判定を先に置いた。
併せて IPv4 の 192.0.0.0/24・198.18/15・240/4、IPv6 の 2001:db8::/32 も拒否に追加。
回帰テスト 4 本（埋め込み private の拒否、埋め込み public の通過、予約帯、DNS64）を追加。

レビューが確認した防御（指摘なし）: リダイレクト再検証に迂回なし（相対・プロトコル相対とも
`join` 後に全検査）、取得内容の漏洩経路なし（`tool_result` とバイト数 summary のみ）、
サイズ上限は Content-Length 非依存で実効、`read_body` のスライス演算にパニック経路なし。

### やらなかったこと

- **DNS リビンディング**（検査時と接続時の再解決差）は残存リスク。閉じるには接続先 IP の
  ピン留めが要り、スコープ外と判断。`web/guard.rs` の冒頭コメントに明記
- `AGENT_APPROVAL=auto` では承認確認が入らない。操作者の明示的選択として README に注記
- 実ネットワークへの疎通確認は未実施（テストはすべてモック）。実際の docs.rs 取得は
  P0 の実 LLM 検証と併せて行うのが自然
