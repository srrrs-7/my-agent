# セッションログに保持上限を設ける

## As-is（現状）

会話ログは既定で有効で、**何も消しません**。`agent sessions --delete <ID>` を手で叩くか
`.agent/sessions/` を自分で消す以外に、減る経路がありません。

育ち方は 2 方向あります。

**① ディレクトリが増える。** `agent chat` も `agent run` も 1 回ごとに新しい
セッションファイルを作ります。`make ask` を 1 日 20 回叩けば 1 日 20 ファイルです。

**② 1 つのファイルが太る。** 再開すると同じファイルに追記が続きます。1 ターンの上限は
「25 反復 × ツール出力 32 KB」（`AGENT_MAX_ITERATIONS` × `AGENT_MAX_TOOL_OUTPUT_BYTES`）で、
最悪 1 ターン 800 KB 前後。同じセッションを何度も再開すると、そのファイルは
セッションをまたいで積み上がり続けます。

体感する形は 3 つです。

| 症状 | なぜ |
|---|---|
| `agent sessions` が遅くなる | `FileSessionStore::list` は要約（通数と冒頭の依頼）を作るために**全ファイルを丸ごと読む** |
| 再開が遅くなる | `load` は履歴を再生するためにそのファイルを丸ごと読む。再開のたびに、それまでの全部を読み直す |
| ディスクが減る | 上限がないため |

そして**会話全文が無期限に残ります**。モデルが読んだファイルの中身を含みます。

なお `search_files` はこれを拾いません（`WalkBuilder` が `hidden(true)` と
`git_ignore(true)` で、`.agent/` は両方に該当）。`list_directory` はワークスペース直下で
`.agent/` を見せますが、それだけです。

## To-be（あるべき姿）

古いセッションは自動で消え、ディスクの使用量とディスクに残る会話の量が予測できる範囲に
収まる。手で消して回る必要がない。

`agent sessions` と再開の速さが、そのマシンで何ヶ月エージェントを使ったかに左右されない。

上限は設定でき、「消したくない」も選べる。

## 影響範囲

- **クレート**:
  - `domain` … `SessionStore` に刈り込みの口を足すかどうか（下のメモ参照）。
    足さない選択なら変更なし
  - `infrastructure` … `session/store.rs`（または新しい `session/rotate.rs`）。
    `list` が全文を読んでいる点も、要約だけ別に持つなら一緒に見直す対象
  - `cli` … 設定の結線。刈り込みを走らせる場所（起動時か、`sessions` に
    `--prune` を足すか）
- **不変条件**: なし（§2 に隣接するが、ログの置き場所の判断は
  `conversation-log-append-only` で済んでいる）
- **設定・ドキュメント**: `.env.example`、`README.md` §3 / §4 / §8、
  `management/docs/architecture.md` §3.2.3
- **利用者への影響**: **既定で有効にすると、これまで残っていた記録が消えるようになる。**
  既定値の選択がそのまま「いつ消えるか」なので、README に明記する。
  既存のログに遡って適用するか、これから作るものだけかも決める

## 達成条件

- [x] 上限を超えた古いセッションが自動で削除される
      （`only_the_newest_sessions_are_kept`、
      `sessions_older_than_the_limit_go_however_few_there_are`）
- [x] 上限の決め方が設定でき、**無効にもできる**（件数と日数。それぞれ独立に `0` で解除。
      `sessions_are_kept_by_count_and_by_age`、
      `zero_means_no_limit_rather_than_delete_everything`、
      `each_retention_limit_can_be_lifted_on_its_own`）
- [→] 1 つのセッションファイル自体が青天井にならない — **別 issue に切り出した**:
      `todo/2026-08-14_session-log-single-file-growth.md`。この issue の「メモ」で
      予告していたとおり、②は 1 セッション 1 ファイルの前提を崩す必要があり、
      不変条件 §4 に触れる案しかないため、①と一緒には入れられない
- [x] 削除が**現在動いているセッションを消さない** — 刈り込みはセッションが作られる前、
      起動時に走る。加えて `--resume` が名指ししたセッションは対象外
      （`a_protected_session_survives_both_rules`）
- [x] 削除に失敗してもエージェントは起動する（`apply_retention` は警告して続行。
      1 ファイルの削除失敗も他を止めない）
- [x] 何を消したかがユーザーに分かる（消えたときだけ stderr に 1 行。
      現在の方針は `agent doctor` の `session retention`）
- [x] `agent sessions` の所要時間が、保持しているセッションの総バイト数に
      比例しなくなる（下の「決めたこと」を参照）
- [x] 既定値と、それが「だいたい何日ぶん」なのかが README に書かれている
- [x] `make check` が緑（323 passed / 0 failed）

## 優先度の根拠

放置するとディスクが減り、`agent sessions` と再開が遅くなり、会話全文が無期限に
溜まり続ける。ただし手で消す回避策があり、低コストなので重要度は `medium`。
実装コストは時期によらず同じだが、**ログは既定で有効なので、今この瞬間から
片付ける対象が増え続ける**ため緊急度も `medium`（score 6 → P2）。

## 決めたこと

### 軸は「件数」と「日数」。容量は入れなかった

`AGENT_SESSION_KEEP`（既定 50）と `AGENT_SESSION_MAX_AGE_DAYS`（既定 30）。
**どちらかを超えたら消える**（AND ではなく OR）ので、「50 件まで、ただし 30 日で消える」。

`0` は**上限の解除**であって「今すぐ全部消す」ではない。誰も後者を意図して打たないし、
そう解釈すると設定が守ろうとしているものを設定自身が壊す。テストで固定した。

容量の軸は入れなかった。容量が効くのは「1 ファイルが巨大」な場合で、それは②の話。
切り出した issue 側に置いた。

### 壁時計をここで使うのは、圧縮の決定と矛盾しない

`recency-weighted-compaction` では「新鮮度に時計を使わない」と決めた。あれは
**モデルが今も見るべき会話の量**の話で、効くのは「それ以降どれだけ会話が進んだか」。

こちらは**転写が誰かのディスクに何日残るか**の話で、保持期間は日で語るのが自然だし、
プライバシーの説明とも噛み合う。同じ「古さ」でも問いが違うので、測り方も違ってよい。
`store.rs` の `RetentionPolicy` にこの区別をコメントで残した。

### ポートには載せず、`FileSessionStore` の inherent method にした

転写がディスクに何日残るかはストレージの性質であって、会話についての規則ではない。
`SessionStore` に載せると、ドメインが他では要らない保持ポリシーと「日」という単位を持つ。

結果として `domain` の変更は `SessionSummary` の形だけになった。

### 走らせるのは起動時。同期でよかった

ログは追記しかしないので、何かが「消す側」にならなければディレクトリは一方向にしか
動かない。起動時が唯一の自然な契機。

非同期にする案も考えたが不要だった。`prune` は**ファイルを 1 つも開かない**
（ディレクトリを 1 回読んで各ファイルを `stat` するだけ）ので、起動時間に乗らない。
失敗は警告して続行する — 片付けが走らなかったことは、エージェントを渡さない理由にならない。

### `--resume` が名指ししたセッションは消さない

これは実装中に気づいた実際の不具合。既定は 30 日で、`--resume <ID>` で古い記録を
名指しするのは**普通の使い方**。刈り込みは起動時＝セッションを選ぶ前に走るので、
保護しないと「開く直前に消す」ことになる。`--resume`（id なし）の場合も、
最新が `max_age` を超えていれば同じことが起きるので `latest()` を保護対象に入れた。

### 一覧が全ファイルを読むのをやめた（`SessionSummary` の形を変えた）

`messages: usize` を落として `bytes: u64` にした。通数は全行を読まないと出せず、
3 つの中で最も情報量が少ない。一覧を見る人が知りたいのは「どれが自分のか」（preview）と
「どれを消すべきか」（サイズ）で、どちらもメタデータと先頭数 KB で答えられる。

preview は先頭 8 KB だけを走査する。**代償は、それより長い冒頭依頼には preview が
付かないこと。**一覧 1 列のために数百 MB を読むよりましだと判断した。この制限自体を
テストで固定してある（`an_opening_request_past_the_scan_window_gets_no_preview`）。

## 結果

- **domain** — `SessionSummary` を `{id, preview, bytes}` に変更（`messages` を削除）
- **infrastructure** — `session/store.rs` に `RetentionPolicy` と
  `FileSessionStore::prune`。`entries()` がメタデータのみを返すよう作り直し、
  `list` / `latest` / `prune` の 3 つが共有。`preview` は先頭 8 KB のみを走査。
  `config` に `AGENT_SESSION_KEEP` / `AGENT_SESSION_MAX_AGE_DAYS` と
  `describe_retention`（`agent doctor` 用）
- **cli** — `composition::apply_retention`（起動時、`--resume` 対象を保護）、
  `sessions` の一覧が通数ではなくサイズを表示（`human_bytes`）
- **ドキュメント** — `.env.example`、README §3 / §4 / §7 / §8、
  `management/docs/architecture.md` §3.2.3
- **テスト** — 10 本追加、313 → 323
- **やらなかったこと**
  - **②（1 ファイルの肥大）** → `todo/2026-08-14_session-log-single-file-growth.md`
  - **一覧が総バイト数に比例しなくなったことは、構造で示していてタイミングでは測っていない。**
    `entries()` がファイルを開かず、`preview` が先頭 8 KB で止まることをコードで
    確認できる形にし、走査窓の制限自体をテストで固定した。所要時間そのものを
    アサートするテストは不安定なので書いていない
  - `apply_retention` の結線（起動時に実際に走ること）はテストで踏んでいない。
    `cli` に `Application` を組む足場がないため。`prune` 本体と設定の解析はテスト済み

## メモ

- **`list` が全ファイルを丸ごと読んでいるのは、この issue で一緒に直す価値がある。**
  通数と冒頭の依頼しか要らないのに履歴全体を再生している。ローテーションを入れても
  「保持している分を毎回全部読む」構造は残る。
  - 案 A: サイドカーの要約ファイル（`<id>.meta.json`）を書く。ファイルが 2 つに
    なるので、`session-persistence-and-resume` で「1 ファイルにする」と決めた理由
    （食い違い）に触れる。要約は再生成できるので、壊れていれば作り直せばよい
  - 案 B: 先頭の数 KB だけ読んで冒頭の依頼を取り、通数は諦める（または行数だけ数える）
- **刈り込みの口をどこに置くか**
  - 案 A: `SessionStore` に `prune(policy)` を足す（ポート変更 = domain に触る）
  - 案 B: `FileSessionStore` の inherent method にして、composition root が呼ぶ。
    ポートは変わらない。**ローテーションはファイルの寿命の話でドメインの規則ではない**
    ので、こちらが素直に見える
- **いつ走らせるか。** 起動時に毎回は、起動を遅くするうえに失敗経路が増える。
  `agent sessions --prune` を明示的に叩く形なら安全だが、自動で消えないと
  この issue の To-be を満たさない。折衷案は「起動時に非同期で 1 回、失敗は無視」
- **②（1 ファイルの肥大）は①より難しい。**単純に古い行を落とすと、再開時の再生が
  途中から始まって `tool_result` が孤児になりうる（不変条件 §4）。
  安全な形の 1 つは「再開のたびに新しいファイルを開き、前のファイルの id を
  ヘッダに記録する」で、そうすると 1 セッション 1 ファイルではなくなる。
  着手時に①だけ先にやって②は分けてもよい
- **既定値の候補**: 件数（例 50 セッション）が説明しやすい。容量（例 500 MB）は
  1 ファイルが巨大なときに効く。日数（例 30 日）はプライバシーの説明と噛み合う。
  どれか 1 つではなく「件数 OR 日数」の組み合わせが実用的かもしれない

  「やらなかったこと」でこれを挙げている）、
  `done/2026-08-14_session-persistence-and-resume.md`（再開が全文を読む理由）
