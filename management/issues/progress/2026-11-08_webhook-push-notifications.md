# Webhook でプッシュ通知を送る（承認待ち・ターン完了・失敗）

## As-is（現状）

エージェントが長いタスクを回している間、終わったか・止まっているかは端末を見ないとわからない。
特に `read-only`（既定）や `ask` の承認ポリシーでは、書き込み系ツールの確認プロンプトで
エージェントが**人の返事を待って止まる**が、離席していると気づけず、その間は何も進まない。

エージェントは Docker コンテナ内で動くため、macOS のネイティブ通知を直接出す手段もない。

## To-be（あるべき姿）

Webhook の URL を設定すると、次のときにスマホやチャットへ通知が届く。

- **承認待ち** — 確認プロンプトを実際に出したとき（どのツールの承認か）
- **ターン完了** — 回答が出たとき。回答の冒頭（既定 100 文字程度）を本文に含む。
  `chat` で毎ターン鳴らないよう、所要時間がしきい値未満のターンは通知しない
- **失敗・反復上限** — プロバイダのエラーや `AGENT_MAX_ITERATIONS` で止まったとき

ntfy / Slack / 汎用 JSON の送信形式を選べる。URL を設定しなければ何も送らない（既定は無効）。
通知の送信に失敗してもエージェントの動作は止まらない。

## 影響範囲

- **クレート**: `domain`（通知の境界）、`infrastructure`（Webhook 送信・設定）、
  `cli`（承認ゲートとコマンドからの発火、合成ルートでの結線、`doctor` 表示）。
  `application`（ループ）は触らない想定 — 設計は `domain-specialist-agent` に確認する
- **不変条件**: §1（application に tokio / infrastructure を持ち込まない）、
  §3（通知の失敗をツール失敗や実行失敗にしない）、§5（テストは生 TCP モックで、ネットワークに出ない）
- **設定・ドキュメント**: 新しい `AGENT_NOTIFY_*` 変数 → `infrastructure/src/config/`、
  `.env.example`、`README.md` §8。機能説明を README に追加
- **利用者への影響**: なし（既定で無効。既存の `.env` と CLI 引数はそのまま動く）

## 達成条件

- [x] Webhook URL 未設定時は通知処理が一切走らない（外向きの通信が発生しない）
- [x] 承認プロンプトを実際に出したときだけ通知される（`auto` ポリシーや非対話の自動拒否では送らない）
- [x] ターン完了の通知が回答の冒頭を含み、文字数上限で切られる（0 で本文に含めない）
- [x] 所要時間がしきい値未満のターン完了は通知されない
- [x] プロバイダ失敗・反復上限で止まったときに通知される
- [x] 送信の失敗・タイムアウトが警告 1 行で済み、エージェントの動作・終了コードに影響しない
- [x] `agent run` で、プロセス終了前に完了通知の送信が（タイムアウト付きで）終わる
- [x] ntfy / Slack / 汎用 JSON それぞれで実際に送出されるリクエストを、
      `agent-test-support` のモックサーバで固定するテストがある
- [x] Webhook URL は秘密情報として扱われ、`agent doctor` やログでマスクされる
- [x] `README.md`（§3・§8）に設定と、本文が外部サーバに出ることの注意が書かれている
      （`.env.example` は最小構成化により必須 3 項目のみ。2026-11-08 方針変更）
- [x] `make check` が緑

## 優先度の根拠

承認待ちで気づかず止まるのは実用上の損失だが、端末を見張るという回避策はある（重要度 medium）。
期限はないが、承認ゲートや出力系に手が入るほど後から差し込む手戻りが増える（緊急度 medium）。

## メモ

- 経路の選択（2026-11-08 ユーザー判断）: ターミナル通知（OSC 9）・外部コマンド（Codex の `notify` 方式）
  ではなく Webhook を採用。本文には回答の冒頭も載せる
- ntfy.sh の公開トピックはトピック名を知っていれば誰でも読める。README で自前サーバか
  推測されにくいトピック名を勧める
- 回答の冒頭はモデルが書いた文字列であり、プロンプトインジェクションで秘密を回答に
  書かせれば Webhook 先へ出ていく。文字数上限はこの経路の帯域制限も兼ねる
- 実装時に決めたこと（2026-11-08, impl-agent）:
  - 失敗通知の理由は `AppError` の本文を使わず、粗い分類（タイムアウト / 認証 / HTTP ステータス等）に
    落とした。`LlmError::Transport` は provider の base_url を、`Api` は応答本文を最大 500 バイト含むため
  - Webhook のリダイレクトは追わない（307 だと本文が別の宛先へ再送されるため）。3xx は送信失敗として警告になる
  - Slack 形式は `& < >` をエスケープする。回答の抜粋に `<!channel>` があると全員にメンションが飛ぶため
  - ntfy / Slack の本文に載せる session id は先頭 8 文字だけ（全体はセッションログのファイル名になる）。
    json 形式は機械処理向けに全体を載せる
  - URL 未設定時も `NullNotifier` へのタスク spawn 自体は起きる（外向き通信はない）。
    spawn まで止めたいならフラグ分岐が要り、設計方針（Null 実装で切り替える）とぶつかる
- 動作検証テスト（2026-11-08, test-agent）:
  - `crates/cli/tests/notify_e2e.rs` — 実バイナリ（`CARGO_BIN_EXE_agent`）を子プロセスで起動し、
    モック LLM とモック Webhook（`agent-test-support` の `RecordingServer`）だけを相手に、
    合成ルート・`run` / `chat`・終了処理まで通す 20 本。`drain` / chat の `drain` を外す、
    承認通知を非対話の自動拒否より前に出す、の 3 つの改変で落ちることを確認済み
  - 承認ゲートの対話経路は TTY が要るため、`CliApprovalGate` に入力関数の差し替え口
    （`#[cfg(test)] with_read_line`、既定は `prompt_line`）を設けて単体で検証した
  - 「URL がログでマスクされる」は stderr の警告について確認。`agent doctor` の表示は未検証
